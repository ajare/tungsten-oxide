# cpp/editor CLAUDE.md

Loads only when working with files under `cpp/editor/` (see the root `CLAUDE.md` for repo-wide guidance).

## Editor conventions

- Editor state lives in `editor::EditorState`, wrapping a single mutable `editor::TrackDefinition` (see `EditorState.hpp`).
- Undo/redo (`EditorHistory.hpp`) uses whole-track deep-clone snapshots (`undoStack_`/`redoStack_`, capped at `kMaxHistory`), not diffs. Every discrete mutation calls `pushUndo()` once *before* mutating, capturing pre-edit state. Continuous gestures (dragging a point, typing in a field) call `pushUndo()` once at gesture start, not per-tick, so one drag = one undo step — see `dragMutated_` for how point-selection-without-dragging avoids recording a no-op step.
- Mesh regions (placed mesh assets, drag-to-move/shift-drag-to-rotate, and the modal Rails mode for flagging rail edges) were removed entirely in `DRIVABLE_MESH_OBJECTS_PLAN.md` Milestone 2, with no interim replacement. `EditMode` is `Edit | Create` now, with `E`/`C` shortcuts; `EditorState`'s generic rotate-gesture plumbing (`beginRotateGesture`/`dragRotateGestureTo`/`endRotateGesture`, see below) survived the removal since it's entity-agnostic and Milestone 5 is expected to attach it to a future drivable-mesh-object entity.
- The top-down canvas's right-click context menu (`TopDownCanvas.cpp`) opens on mouse-*release* only when the accumulated right-drag delta is negligible (< 3px) — a real drag still pans, since the drag delta is reset only on release, after the drag's own per-frame pan deltas already applied.
- All mode changes go through `setMode()` — it clears the abandoned create draft and syncs the dropdown, so the `E`/`C` keys and the dropdown can't drift.
- The top-down grid has a visible checkbox and `G` shortcut. Hiding it temporarily disables both the grid-size control and snapping; the Snap checkbox retains its preference so showing the grid restores the prior snap setting. `TopDownView::snapWorldXZ()` also checks visibility directly, so disabled UI cannot leave hidden-grid snapping active.
- Bundled texture assets are stored as `"assets/track/..."`, relative to the repo root. `cpp/editor/src/TextureCache.cpp`'s `get()` resolves a relative path against `findAssetsDir()`'s parent (the repo root), so track_editor.exe can be launched from any working directory (e.g. `cpp/build/editor/Release`) and still find the same on-disk texture.
- `ProjectionMode` (`EditorState.hpp`) is a second, canvas-wide mode — `TopDown | Front | Side` — orthogonal to `EditMode`: it picks which plane a screen drag projects into, not what a click/drag does semantically. Toolbar dropdown + `1`/`2`/`3` shortcuts. Default `TopDown`, matching the editor's original (and, before `DRIVABLE_MESH_OBJECTS_PLAN.md`, only) behavior. Both `setMode()` and `setProjectionMode()` drop any in-flight drag/rotate gesture, so switching planes or edit modes mid-gesture can never leave a dangling half-mutation.
- Drag-to-move and shift+drag-to-rotate are generalized per `ProjectionMode` via `planeCoords`/`setPlaneCoords` (`EditorState.hpp`, mirrored by a matching free `planeCoords` in `TopDownCanvas.cpp` so rendering stays in step): `TopDown` reads/writes `(x, z)` — today's only behavior for every entity — `Front` reads/writes `(x, y)`, `Side` reads/writes `(y, z)`. The third axis outside the active plane is left untouched by a drag. Position-point hit-testing/dragging/rendering (`hitTestPosition`/`withinPick`/`selectPositionAt`/`hoverTestPosition`/`dragSelectedTo`, `drawAuthoredPositionPoints`) all go through this; everything else on the canvas (weld/join-drag endpoint search, zones/triggers/road) is still `TopDown`-only. The rotate gesture's math (`TopDownCanvas.cpp`'s `rotateAngleDeg`) is generalized the same way — `TopDown` → yaw, `Front` → pitch, `Side` → roll, all the same `atan2` convention fed different plane axes — but as of Milestone 1.3 has no entity wired to it yet (`EditorState`'s `beginRotateGesture`/`dragRotateGestureTo`/`endRotateGesture` just track the angle); Milestone 5 attaches it to drivable mesh object placements.
- `ElevationView` (the separate arc-length-profile side panel) is retired (`DRIVABLE_MESH_OBJECTS_PLAN.md` Milestone 1.4). Position-point height editing lives entirely in Front canvas mode now — dragging a point there moves `(x, y)` together via the same generalized `dragSelectedTo` as any other plane. Its right-click-to-insert-a-point feature was *not* carried forward: inserting a new point is inherently an X/Z-topology operation (the existing top-down canvas context menu's "Add control point" already covers it), so Front/Side stay editing-only, not point-creation surfaces.
- A Track resource's `<Models>` list (`TRACK_MODEL_LIST_PLAN.md`) replaced the old single `<TrackData>`/`<ModelFile>` pair — the editor still authors exactly one Track-type Model per session (`EditorState` stays single-`TrackDefinition`; true multi-document editing of several independently-baked TrackData files is out of scope), but `editor::TrackDefinition::models` carries every other (Physical/Decorative prop) `<Model>` entry as outer-XML-only data, excluded from `fromJson`/`toJson`'s schema-10/12 JSON but included in whole-document undo/redo snapshots like everything else. "Load Model..." (`main.cpp`, replacing the old "Place Drivable Mesh Object...") picks a `.mppmodel` or standalone `<Model>` XML (classified independently of `cpp/model-tool`'s own `OpenTarget.cpp`) and calls `EditorState::loadModel`, which dedups by `ModelFile` (reusing an existing embedded entry rather than duplicating it) before adding a placement — `findModel`/`editEmbeddedModel` mirror the existing `findMeshObjectPlacement`/`editMeshObjectPlacement` pattern for the Properties panel's per-mesh Type/Visible editor. `TopDownCanvas.cpp`'s `drawMeshObjectPlacements` renders a placement's real geometry (loaded via `MppModelImport.hpp`'s reader, cached per resolved path for the process's lifetime) under the existing diamond-marker handle, transformed by the placement's 6-DOF transform and projected through `worldToScreenPlane` like every other shape on this ImGui-drawlist-only canvas — there is no real 3D OpenGL rendering here at all. `MppModelImport.hpp`/`MppModelExport.hpp` are no longer mpp-free (`docs/GLTF_IMPORT_PLAN.md` M4): both are now thin wrappers over `cpp/model-io`'s `mpp::ModelSerializer`-backed reader/writer, and accept/emit both the 36-byte legacy and 52-byte PBR vertex layouts.
